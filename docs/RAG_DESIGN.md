# RAG 설계 초안

작성: 2026-09-20 / 상태: 초안 v1 [제안]
관련: `PROJECT.md` 6장(데이터), 9장(F5·F6·F9·F10), `docs/EXTERNAL_APIS.md`

## 1. 결론 요약

- **검색 엔진: Apache Lucene을 데몬에 내장한다.** 벡터 검색(HNSW)과 한국어 키워드 검색(Nori 형태소 분석기, BM25)을 한 인덱스에서 함께 쓰는 하이브리드 검색으로 간다.
- **임베딩: 로컬 Ollama의 `bge-m3`를 기본값으로 한다.** 다국어(한·영 교차 검색 가능), 1024차원, 비용 0, 자료가 밖으로 나가지 않는다. API 임베딩은 설정으로 바꿀 수 있는 대안으로 둔다.
- **원문은 SQLite, 인덱스는 파생물.** Lucene 인덱스는 언제든 지우고 다시 만들 수 있어야 한다.
- **모든 검색은 "기준 시점(asOf)"을 받는다.** 그 시점에 시스템이 알 수 있었던 문서만 검색된다. 백테스트와 AI 학습(F10)의 신뢰성이 여기에 달려 있다.
- **숫자는 RAG로 찾지 않는다.** 시세·재무 수치·보유 현황은 DB와 API에서 구조화된 값으로 가져온다. RAG는 글(공시, 뉴스, 리포트, 과거 토론, 회고)만 다룬다.

## 2. 무엇에 쓰는가

| 용도 | 기능 | 검색 내용 | 비고 |

| 시장 전망 리포트 | F9 | 기간 내 거시·업종·시장 뉴스, 직전 리포트 | 종목이 아니라 주제·기간 중심 질의 |

| 종목 질의응답 | 화면 | "이 종목 지난주에 왜 빠졌지?" 같은 사용자 질문 | 답변에 출처 링크 표시 |

**쓰지 않는 곳.** 현재가, 재무 수치, 밸류에이션 계산, 보유·체결 내역, 가드레일 판단. 이들은 LLM에 도구 호출(tool calling) 또는 프롬프트의 구조화 블록으로 전달한다. 임베딩 검색으로 숫자를 찾게 하면 다른 분기·다른 종목의 숫자가 섞여 들어오는 사고가 난다.

## 3. 기술 선택

### 3.1 검색 엔진 비교

| 후보 | 판단 |
|---|---|
| **Apache Lucene (내장)** | **채택.** 순수 Java라 데몬에 그대로 들어가고 별도 프로세스가 없다(D7의 "임베디드" 원칙과 일치). 벡터·키워드·메타데이터 필터를 한 질의로 처리. Nori로 한국어 형태소 분석. int8 양자화로 인덱스 크기 절감 가능 |
| sqlite-vec / sqlite-vss | SQLite 하나로 끝나는 장점이 있으나 JDBC에서 네이티브 확장을 로드해야 하고, 한국어 키워드 검색과 하이브리드 결합이 약하다 |
| pgvector | PostgreSQL 설치가 필요해 임베디드 원칙에 어긋난다 |
| Chroma / Qdrant / Milvus | 별도 서버 프로세스. dmg 하나로 배포하는 구조와 맞지 않는다 |
| Spring AI `SimpleVectorStore` | 메모리 상주 + JSON 파일. 수십만 청크 규모와 필터 검색에 부적합 |

주의: Lucene의 벡터 차원 상한은 기본 1024다. `bge-m3`(1024)는 그대로 들어가고, OpenAI `text-embedding-3` 계열을 쓸 때는 `dimensions` 파라미터로 1024 이하로 줄여 받는다.

### 3.2 임베딩 모델

| 후보 | 판단 |
|---|---|
| **Ollama `bge-m3` (로컬)** | **기본값.** 다국어, 1024차원, 긴 입력(8K 토큰) 지원. 한국어 질의로 영어 문서(SEC 공시, 미국 뉴스)를 찾는 교차 검색이 된다. Mac mini에서 상시 구동 부담이 작다 |
| OpenAI `text-embedding-3-small/large` | 품질 안정적, 설치 불필요. 자료가 외부로 나가고 비용이 든다. Ollama를 돌리기 부담스러운 노트북용 대안 |
| Voyage / Cohere multilingual | 검색 품질 평가에서 강한 편. 3단계에서 비교 실험 대상 |

**모델을 바꾸면 인덱스 전체를 다시 만들어야 한다.** 그래서 (1) 인덱스에 모델 식별자와 차원을 기록하고 불일치 시 기동을 막으며, (2) 원문을 SQLite에 보관해 재색인이 가능하게 하고, (3) 멀티 디바이스 환경에서 디바이스마다 다른 모델을 써도 되도록 **인덱스는 동기화하지 않는다**(PROJECT.md 6장과 일치).

### 3.3 Spring AI와의 관계

임베딩 호출은 Spring AI의 `EmbeddingModel` 추상화를 쓴다(제공자 교체가 설정만으로 된다). 검색 쪽은 Spring AI의 `VectorStore` 인터페이스에 맞추지 않고 **자체 포트 `KnowledgePort`** 를 `core.port`에 정의한다. 기준 시점 필터, 하이브리드 결합, 시간 감쇠 같은 요구가 `VectorStore`의 범용 인터페이스로는 표현되지 않기 때문이다.

## 4. 데이터 모델

### 4.1 두 개의 코퍼스

| 코퍼스 | 내용 | 범위 |
|---|---|---|
| **공용(PUBLIC)** | 공시, 뉴스, 거시 지표 해설, 시장 리포트 | 개인정보 없음. 디바이스당 하나 |
| **개인(USER)** | 토론 기록, 추천 기록, 매매 일지 메모, 회고 | `userId`별로 분리. 검색 시 `userId` 필터를 어댑터가 강제한다(호출자가 빠뜨릴 수 없게) |

가족 공유 학습(D16)으로 받은 회고는 금액·수량이 제거된 형태로 **공유(FAMILY)** 범위에 들어간다.

### 4.2 저장 구조

```
SQLite (원본, 재색인의 출처)
  knowledge_document   문서 단위: id, scope, docType, source, url, title, publishedAt,
                       firstSeenAt, contentHash, supersedesId, rawText(또는 요약)
  knowledge_symbol     문서 ↔ 종목 연결 (N:M), 연결 근거(제목 일치/본문 일치/공시 주체)

Lucene (파생 인덱스, 삭제 후 재생성 가능)
  청크 단위 문서: chunkId, docId, scope, userId, market, symbols[], docType, source,
                 publishedAt, firstSeenAt, text(Nori 분석), vector(1024, int8 양자화),
                 embeddingModel
```

### 4.3 문서 유형별 처리

| 유형 | 출처 | 청킹 | 보관 |
|---|---|---|---|
| 국내 공시 | DART `document` | 절(section) 단위 → 800~1,200자, 표는 텍스트로 풀되 숫자 표는 색인 제외 | 원문 전체. 사업보고서는 "사업의 내용", "위험 요소", "경영진단" 등 필요한 절만 |
| 미국 공시 | SEC EDGAR | 10-K/10-Q의 Item 단위(Business, Risk Factors, MD&A) | 동일 |
| 뉴스 | 네이버 검색 API, RSS | 기사당 1청크(제목+요약) | **제목·요약·링크·발행 시각만 저장.** 본문 전문은 허용된 소스에 한해서만 |
| 시장 리포트 | 자체 생성(F9) | 단락 단위 | 전문 |
| 토론 기록 | 자체 생성(F6) | 결론 요약 1청크 + 페르소나별 핵심 논거 | 전문은 SQLite, 색인은 요약만 |
| 회고 | 자체 생성(F10) | 사례당 1청크: 상황 요약 / 당시 판단 / 실제 결과 / 교훈 | 전문 |

**청크 머리말.** 임베딩 전에 각 청크 앞에 `[삼성전자(005930)] [사업보고서 2025] [위험 요소]` 같은 맥락 머리말을 붙인다. 청크만 떼어 놓으면 어느 회사의 어느 문서인지 사라지는 문제를 막는다.

**종목 연결.** 뉴스에는 종목코드가 없으므로 종목명·별칭 사전(종목 마스터 + 수동 별칭)으로 매칭한다. 동음이의(예: 일반 명사와 같은 종목명) 오탐을 줄이기 위해 제목 일치를 본문 일치보다 높게 치고, 연결 근거를 저장한다.

**중복 제거.** 통신사 기사는 여러 매체에 중복 게재된다. 정규화한 본문의 해시와 유사도(SimHash)로 중복을 묶고 대표 1건만 색인한다. 중복 건수는 "화제성" 신호로 메타데이터에 남긴다.

**정정.** 정정 공시는 이전 문서를 지우지 않고 `supersedesId`로 연결한다. 기본 검색은 최신본만, 기준 시점 검색은 그 시점에 유효했던 판본을 돌려준다.

## 5. 기준 시점(point-in-time) 원칙

모든 문서는 두 시각을 가진다. `publishedAt`은 출처가 말하는 발행 시각이고, `firstSeenAt`은 **우리 시스템이 처음 수집한 시각**이다. DART처럼 발행 시각이 날짜까지만 제공되는 소스가 있고, 뉴스도 사후에 수정되므로, 신뢰할 수 있는 것은 `firstSeenAt`뿐이다.

- `KnowledgePort.search(...)`는 `asOf`를 **필수 인자**로 받는다. 실시간 사용에서는 `clock.instant()`를 넘긴다.
- 어댑터는 항상 `firstSeenAt <= asOf` 필터를 건다.
- 수집을 시작하기 전의 과거 문서를 소급 수집한 경우, `firstSeenAt`은 "발행일 다음 거래일 장 시작 시각"으로 보수적으로 설정하고 `backfilled=true`로 표시한다.
- F10의 성과 대조와 스크리닝 백테스트는 반드시 과거 `asOf`로 검색한다. 이 규칙은 고정 시계를 쓴 테스트로 검증한다.

## 6. 검색 파이프라인

```
질의 구성 → 필터 확정 → [BM25 검색] + [벡터 kNN 검색] → RRF 결합
         → 시간 감쇠 → 다양성(MMR) → (선택) 리랭커 → 상위 k개 + 출처
```

1. **질의 구성.** 호출자(토론 엔진 등)가 자연어 질의와 구조화 조건을 함께 넘긴다: 종목, 시장, 문서 유형, 기간, 범위(PUBLIC/USER/FAMILY), `asOf`. 페르소나별 질의 템플릿을 둔다.
2. **필터.** 종목·유형·기간·범위·`asOf`는 Lucene 필터로 먼저 좁힌다. 벡터 검색도 필터 안에서 수행한다.
3. **하이브리드.** BM25(Nori)와 kNN 결과를 RRF(Reciprocal Rank Fusion)로 합친다. 종목명·고유명사·숫자가 든 질의는 키워드가, 개념적 질의("수익성 악화 우려")는 벡터가 강하다.
4. **시간 감쇠.** 문서 유형별 반감기를 둔다. 뉴스는 짧게(수일~수주), 공시·사업보고서는 길게, 회고는 감쇠 없음.
5. **다양성.** 같은 사건을 다룬 비슷한 청크가 상위를 독점하지 않도록 MMR로 중복을 누른다.
6. **리랭커(3단계에서 검토).** 교차 인코더 리랭킹은 품질을 올리지만 지연과 의존성이 늘어난다. 평가 세트로 효과를 확인한 뒤 도입한다.
7. **결과.** 청크 텍스트 + `docId`, 제목, 출처 URL, 발행 시각. 기본 k는 8~12, 급등 재료 확인은 3~5.

### 포트 초안

```java
// core.port
public interface KnowledgePort {
    List<KnowledgeHit> search(KnowledgeQuery query);      // query.asOf() 필수
    void index(KnowledgeDocument document);                // 수집 파이프라인이 호출
    IndexStatus status();                                  // 모델 식별자, 문서 수, 마지막 색인 시각
}

public record KnowledgeQuery(
    String text, Set<StockCode> symbols, Set<DocType> docTypes,
    Scope scope, UserId userId, Instant from, Instant asOf, int topK) {}
```

`core`에는 인터페이스와 record만 두고, Lucene·Ollama 의존은 `engine.knowledge` 어댑터에 가둔다.

## 7. 수집·색인 파이프라인

```
수집(포트별 스케줄러) → 정규화 → 중복 제거 → 종목 연결 → SQLite 저장(firstSeenAt 기록)
   → 청킹 → 임베딩(배치) → Lucene 색인 → 이벤트 발행(새 공시/뉴스 도착)
```

- 수집 주기: 공시 1~2분(장중), 뉴스 5~10분, 거시·리포트 일 1회. 각 API의 호출 한도는 `docs/EXTERNAL_APIS.md` 기준.
- 색인은 비동기 큐로 처리하고 가상 스레드로 임베딩 호출을 병렬화한다. Lucene `IndexWriter`는 프로세스에 하나만 둔다(단일 작성자).
- 임베딩 실패(Ollama 미기동 등) 시에도 **키워드 색인은 먼저 완료**하고 벡터는 나중에 채운다. 검색은 벡터가 없으면 BM25만으로 동작한다(기능 저하이지 장애가 아니다).
- "새 문서 도착" 이벤트는 가드레일(악재 공시 → 자동 매수 제외)과 토론 자동 실행의 트리거가 된다. 이 경로는 RAG 검색과 무관하게 동작해야 하므로 색인 완료를 기다리지 않는다.
- 보존: 뉴스는 기본 2년, 공시·리포트·토론·회고는 무기한. 오래된 뉴스는 색인에서만 빼고 SQLite의 메타데이터는 남긴다.

### 규모 추정

1024차원 float 벡터는 청크당 약 4KB, int8 양자화 시 약 1KB. 관심 종목 중심으로 2년 운영 시 수십만 청크 → 인덱스 1GB 안팎. Mac mini와 노트북 모두 부담 없는 수준이다. 전 종목 뉴스를 무차별 수집하지 않고 **보유·관심·후보 종목 + 시장 전반 뉴스**로 범위를 제한한다.

## 8. LLM에 넘기는 방식과 안전

- 검색 결과는 `[S1] 제목 / 출처 / 발행일 / 본문` 형태의 번호 붙은 자료 블록으로 넘기고, **LLM에게 주장마다 출처 번호를 달게 한다.** 토론 결론 레코드에 인용된 `docId` 목록을 저장하고 화면에서 원문 링크로 보여 준다.
- 출처 없는 사실 주장은 사회자 단계에서 걸러 "근거 없음"으로 표시한다.
- **검색된 글은 신뢰할 수 없는 입력이다.** 뉴스·게시물에 "이 종목을 즉시 매수하라" 같은 문장이 있어도 그것은 자료일 뿐 지시가 아니다. 프롬프트에서 자료 블록을 명확히 구분하고, 어떤 경우에도 LLM 출력은 스키마 검증과 가드레일을 거쳐야 주문으로 이어진다(PROJECT.md 10.4). RAG는 이 경계를 바꾸지 않는다.
- 개인 코퍼스의 내용은 외부 LLM API로 나간다는 점을 사용자 설정 화면에 명시하고, 로컬 LLM만 쓰는 옵션을 둔다.

## 9. 평가와 학습 연결

- **검색 품질 평가 세트.** "질의 → 나와야 할 문서" 쌍을 30~50개 직접 만들어 두고, 설정(청크 크기, RRF 가중, 반감기, 모델)을 바꿀 때마다 재현율@k를 잰다. 감으로 튜닝하지 않는다.
- **F10과의 연결.** 토론마다 어떤 자료가 인용되었는지 남으므로, 결론이 크게 틀린 사례에서 "자료가 없었나, 있었는데 못 찾았나, 찾았는데 잘못 해석했나"를 구분할 수 있다. 이 분류가 회고문의 한 항목이 된다.

## 11. 구현 단계

| 단계 | 범위 | 효과 |
|---|---|---|
| R1 | 수집 → SQLite 저장(`firstSeenAt`) → **BM25 + 메타데이터 필터만** | 임베딩 없이도 "종목별 최근 공시·뉴스" 조회와 급등 재료 확인이 된다. 토론의 최소 시드 자료 확보 |
| R2 | 임베딩(Ollama `bge-m3`) + 하이브리드 검색 + 청크 머리말 + 중복 제거 | 개념적 질의, 한·영 교차 검색 |
| R3 | 개인·가족 코퍼스(토론·회고), 시간 감쇠·MMR 튜닝, 평가 세트, 리랭커·모델 비교 실험 | F10 회고 메모리 완성 |

R1은 PROJECT.md 개발 3단계, R2는 4단계, R3는 5단계와 함께 진행한다.

## 12. 확인이 필요한 사항

1. 임베딩 기본값을 로컬 Ollama로 하는 안 — Mac mini에는 맞지만, 밖에서 쓰는 Mac에서도 Ollama를 띄울지, 그쪽은 API 임베딩으로 갈지
2. 뉴스 수집 범위를 "보유·관심·후보 종목 + 시장 전반"으로 제한하는 안
3. 개인 코퍼스(토론·회고)가 외부 LLM API로 전달되는 것에 대한 방침 → `docs/LLM_ROUTING.md` 8장의 "사용자별·제공자별 개인 데이터 전송 허용 스위치"로 다룬다
