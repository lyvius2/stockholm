# 키 관리와 최초 구동 설계

작성: 2026-09-20 / 상태: v2 — 9장 세 항목 확정 반영
관련: `PROJECT.md` 2장(D10·D17·D18), 5장, 6장 · `docs/LLM_ROUTING.md` · `docs/EXTERNAL_APIS.md`

## 1. 확정 사항

- **가족은 같은 디바이스 하나를 함께 쓴다는 전제다.** 한 설치(데몬 하나)에 최대 4명의 사용자 계정이 있다. [확정]
- **키는 최초 구동 시 강제로 입력받고, 그 이후에는 admin의 변경·삭제 외에는 입력받지 않는다.** [확정]
- **서비스 키는 가족이 공유한다.** LLM, DART, 뉴스, Slack 등은 admin이 한 번 입력해 설치 전체가 함께 쓴다. [확정]
- **토스증권 키와 금융결제원 사용자 토큰은 개인 키다.** 각 구성원이 자기 계정으로 처음 로그인할 때 한 번 강제로 입력하고, 본인 계좌만 매매한다. [확정]
- **필수 입력은 핵심만.** LLM 제공자 1개 이상 + DART(admin), 본인 토스 키(각 구성원). 나머지는 건너뛸 수 있고 나중에 admin이 추가한다. [확정]
- **다른 디바이스를 쓰게 되면 키를 암호화해 서버를 통해 전달·동기화한다.** [확정]

이하 세부 규칙은 [제안]이다.

## 2. 키 분류

| 키 | 분류 | 입력자 | 시점 | 필수 |
|---|---|---|---|---|
| LLM: OpenAI, Claude, DeepSeek 키 / Ollama 주소 | 공유 | admin | 최초 구동 | **1개 이상** |
| DART 인증키 | 공유 | admin | 최초 구동 | **필수** |
| 네이버 검색, KRX, 공공데이터포털, ECOS, FRED, Finnhub 등 | 공유 | admin | 최초 구동 또는 이후 | 선택 |
| 한국투자증권 KIS(정보 수집용, admin 계좌 기반) | 공유 | admin | 이후 | 선택 |
| Slack 봇 토큰 | 공유 | admin | 이후 | 선택 |
| 금융결제원 앱 자격(client id/secret) | 공유 | admin | 이후 | 선택 |
| relay 서버 주소, SMTP(relay 쪽) | 공유 | admin | 서버 연결 시 | 선택 |
| **토스증권 client_id / client_secret / 계좌** | **개인** | 본인 | 본인 최초 로그인 | **필수** |
| **금융결제원 사용자 토큰** | **개인** | 본인(OAuth 동의 화면, 직접 타이핑하지 않음) | 자산 조회 기능을 처음 쓸 때 | 선택 |
| Slack 수신 계정(본인 Slack 사용자) | 개인 | 본인 | 알림 설정 시 | 선택 |

금융결제원은 "앱 자격"과 "사용자 토큰"이 나뉜다. 앱 자격은 이용 신청을 한 사람(admin)의 것이고 서비스 키처럼 공유하며, 각 구성원은 동의 절차를 거쳐 본인 토큰을 받는다.

**공용 시세 수집에 쓰는 토스 키.** 급등 탐지·스크리닝·캔들 캐시 같은 공용 시세 수집에도 토스 API 자격이 필요한데 토스 키는 개인 키다. **admin의 토스 키로 공용 수집을 하고, 주문·계좌·보유 조회는 반드시 해당 사용자 본인의 키로만 한다. [확정]** 토스 약관의 "본인 매매 목적 한정"에 비추어 공용 수집이 문제 되지 않는지 확인이 필요하다. 문제가 된다면 각 사용자의 자동화는 본인 키로만 시세를 받도록 바꾼다(호출량이 최대 4배가 되지만 한도는 키별이라 감당 가능). [확인 필요]

## 3. 최초 구동 흐름

앱을 처음 실행하면 메인 화면 대신 설정 마법사가 뜨고, 끝내기 전에는 다른 화면으로 갈 수 없다. 첫 화면에서 둘 중 하나를 고른다.

### 3.1 새로 설정 (이 디바이스가 첫 설치)

1. **admin 계정 생성.** 처음 설정하는 사람이 admin이 된다. 비밀번호 + TOTP 등록.
2. **공유 키 입력.** LLM 제공자 1개 이상과 DART는 필수, 나머지는 "나중에" 가능.
3. **즉시 검증.** 입력한 키마다 가벼운 실제 호출로 유효성을 확인한다(LLM은 최소 토큰 호출, DART는 기업개황 1건). 검증에 실패한 키는 저장하지 않는다. 필수 키가 검증될 때까지 다음 단계로 못 간다.
4. **admin 본인의 토스 키 입력과 검증**(계좌 목록 조회로 확인, 주문 API는 호출하지 않는다). 사용할 계좌 선택.
5. **LLM 프리셋 선택**(`docs/LLM_ROUTING.md` 4장). 등록된 제공자만으로 경로가 구성된다.
6. **구성원 자리 만들기**(선택). 최대 3명. 각 자리에 1회용 등록 코드를 발급한다.

### 3.2 구성원의 최초 로그인 (같은 디바이스)

1. 로그인 화면에서 "구성원 등록" → admin에게 받은 1회용 코드 입력.
2. 본인 비밀번호 + TOTP 등록.
3. **본인 토스 키 입력과 검증, 계좌 선택.** 끝내기 전에는 메인 화면으로 못 간다.
4. 개인 데이터 전송 허용 여부 등 개인 설정(`docs/LLM_ROUTING.md` 8장).

구성원은 공유 키를 입력하지도, 보지도 않는다.

### 3.3 기존 설치에 연결 (다른 디바이스)

1. relay 서버 주소 입력 → 본인 계정 로그인(비밀번호 + TOTP).
2. 새 디바이스가 키쌍을 만들고 등록을 요청한다.
3. **이미 등록된 디바이스에서 승인한다**(step-up 인증). 서버는 신뢰 대상이 아니므로 승인과 키 포장은 서버가 아니라 기존 디바이스가 한다.
4. 기존 디바이스가 공유 키 묶음과 해당 사용자의 개인 키를 **새 디바이스의 공개키로 감싸** 서버를 통해 보낸다. 서버는 암호문만 중계한다.
5. 새 디바이스는 받은 키를 자신의 Keychain에 넣는다. 이 경로에서는 키를 손으로 입력하지 않는다.

키를 가진 기존 디바이스가 온라인이어야 새 디바이스를 추가할 수 있다. 이후 admin이 키를 바꾸면 같은 경로로 모든 디바이스에 전파된다.

## 4. 이후의 변경 규칙

| 대상 | 변경·삭제 | 값 조회 |
|---|---|---|
| 공유 키 | **admin만.** step-up 인증 필요. 변경 시 즉시 재검증 | **누구도 불가**(admin 포함) |
| 개인 키(토스) | 본인만 교체 가능(토스에서 secret을 재발급한 경우 등). admin은 **삭제만** 가능하며, 삭제되면 그 구성원은 다음 로그인 때 다시 입력해야 한다 | 누구도 불가 |
| 금융결제원 사용자 토큰 | 본인의 재동의로만 갱신. 본인·admin 모두 해제 가능 | 누구도 불가 |

- **키 값은 쓰기 전용이다.** 저장된 키 값을 돌려주는 API나 화면은 만들지 않는다. 화면에는 등록 여부, 끝 4자리, 마지막 검증 시각, 상태만 보인다.
- 키 설정 화면은 admin에게만 보인다. 구성원에게는 "어떤 기능이 키가 없어 꺼져 있는지"만 보이고 "admin에게 요청" 안내가 나온다.
- "admin의 변경·삭제 외에는 입력받지 않는다"는 원칙의 유일한 예외가 **개인 토스 키의 본인 교체**다. admin이 구성원의 토스 키를 대신 입력하면 admin이 그 값을 알게 되므로, 개인 토스 키만은 일반 사용자 본인이 교체할 수 있다. 교체 시 step-up 인증과 즉시 검증을 거친다. [확정]
- 모든 키 등록·교체·삭제·검증 실패는 감사 로그에 남긴다(값은 남기지 않는다).

## 5. 저장

- 키 값은 DB에 넣지 않고 **macOS Keychain**에 둔다. 항목은 `wavestock/shared/{keyName}`, `wavestock/user/{userId}/{keyName}`으로 나눈다. DB에는 메타데이터(종류, 상태, 끝 4자리, 검증 시각)만 둔다.
- 데몬은 포트 `SecretStorePort`로만 Keychain에 접근한다. `engine.secret` 밖에서 키 값을 문자열로 들고 다니지 않도록, 어댑터가 필요할 때 포트에서 직접 받아 쓴다. 로그·예외 메시지·`toString()`에 값이 나오지 않게 전용 타입(`SecretValue`)으로 감싼다.

### 같은 디바이스를 함께 쓸 때의 격리 수준 — 정직한 설명

가족이 같은 macOS 계정으로 같은 Mac을 쓰면, Keychain은 가족 구성원 사이를 구분해 주지 않는다. 데몬은 24시간 떠서 각 구성원의 자동 매매를 무인으로 수행해야 하므로 각자의 토스 키를 스스로 꺼내 쓸 수 있어야 한다. 따라서 **구성원 간 키 격리는 앱 수준의 접근 통제이지 암호학적 격리가 아니다.** 또한 admin은 빌드를 배포하는 사람이므로 기술적으로 신뢰 대상이다. 이 구조가 막아 주는 것은 다른 구성원의 우발적 접근, 화면·API를 통한 키 노출, 기기 도난 시의 유출(FileVault + Keychain)이다.

더 강한 격리를 원하면 선택지가 있다. 개인 키를 본인 비밀번호에서 유도한 키로 한 번 더 감싸 두고, 본인이 로그인했을 때만 풀어 메모리에 올리는 방식이다. 이 경우 Mac이 재부팅되면 각 구성원이 한 번 로그인할 때까지 그 사람의 자동화가 멈춘다(Slack으로 안내). 기본값은 편의 쪽(Keychain 직접 보관)으로 두고, **구성원별 옵션으로 제공한다. [확정]** 옵션을 켠 구성원에게는 "재부팅 후 로그인 전까지 자동화 정지"를 설정 화면에서 분명히 알린다.

## 6. 기능 활성화와 키 상태

- 키가 없는 기능은 숨기지 않고 **비활성 상태와 사유**를 보여 준다.
- 데몬은 주기적으로(하루 1회 + 호출 실패 시) 키 유효성을 확인한다. 만료·폐기·한도 초과가 감지되면 admin에게 Slack 알림을 보내고, 그 키에 의존하는 자동화는 안전한 쪽으로 멈춘다(LLM 전부 실패 시의 정책은 `docs/LLM_ROUTING.md` 7장, 토스 키 실패 시 해당 사용자의 자동화 정지).
- 가정용 회선의 공인 IP가 바뀌면 토스 API가 403을 낸다(허용 IP 사전 등록 제약). 데몬은 공인 IP 변화를 감지해 해당 사용자들에게 "토스 설정에서 허용 IP를 갱신하라"는 알림을 보낸다.

## 7. 이 결정이 다른 설계에 주는 영향

- **사용자 등록부는 클라이언트에 있다.** 한 디바이스에 여러 사용자가 있으므로 "최대 4명" 제한과 계정 관리는 클라이언트(설치)가 1차로 갖고, relay 서버에 연결하면 그 등록부를 서버에 반영한다. 서버 없이도 가족 4명이 쓸 수 있다.
- **데몬 하나가 여러 사용자의 자동화를 동시에 돌린다.** 스케줄러·lease·노출액·가드레일은 모두 `userId` 단위로 동작하고, UI는 로그인한 사용자의 것만 보여 준다.
- **LLM 비용은 admin이 부담한다.** 키가 공유되므로 `ProviderRegistry`는 사용자별이 아니라 설치 단위로 제공자를 보관한다. 사용 기록은 여전히 사용자별로 남기고, 예산은 "설치 전체 일일 예산 + 구성원별 몫"을 admin이 정한다. LLM 경로(목적 → 제공자·모델)도 admin이 관리한다. 구성원은 자기 페르소나에 admin이 열어 둔 제공자 중에서 고를 수 있다.
- **개인 데이터 전송 허용 스위치는 구성원 각자의 것으로 남긴다.** 키는 공유하지만 자기 자료를 어느 제공자에 보낼지는 본인이 정한다.
- **토스 IP·토큰 제약이 크게 완화된다.** 주 사용 환경이 집의 한 디바이스이므로 허용 IP는 집 회선 하나면 되고, 사용자당 토큰을 쓰는 디바이스도 하나다. "다른 디바이스"는 부차 시나리오가 되며, 그때는 3.3의 키 전달과 함께 토큰도 사용자 동기화 키로 암호화해 공유하고 발급은 lease 보유 디바이스만 한다.
- **키도 동기화 대상이 된다.** 기존의 "API 키는 디바이스별 등록"을 대체한다. 공유 키는 가족 공유 키로, 개인 키는 사용자 동기화 키로 암호화되어 이동하며 서버는 내용을 볼 수 없다.

## 8. 테스트

- 마법사를 끝내기 전에는 다른 로컬 API가 모두 거부되는지(설정 미완료 상태의 접근 통제).
- 필수 키 없이 완료할 수 없는지, 검증 실패한 키가 저장되지 않는지.
- 구성원 세션으로 공유 키 변경 API를 호출하면 거부되는지, admin 세션이라도 step-up 없이는 거부되는지.
- **어떤 API 응답·로그·예외·감사 로그에도 키 값이 나타나지 않는지**(테스트용 표식 값을 넣고 전 출력에서 검색).
- 사용자 A의 세션으로 사용자 B의 토스 어댑터가 절대 선택되지 않는지.
- 5번째 사용자 등록이 거부되는지.
- Keychain은 `SecretStorePort`의 메모리 구현으로 대체해 테스트한다.

## 9. 확정된 사항 (2026-09-20)

1. 개인 토스 키는 admin이 아닌 **일반 사용자 본인도 교체할 수 있다**(4장). admin은 삭제만 가능.
2. 공용 시세 수집에는 **admin의 토스 키**를 쓴다(2장). 주문·계좌·보유 조회는 항상 본인 키. 약관상 문제가 확인되면 각자 본인 키로 시세를 받는 방식으로 바꾼다.
3. 개인 키의 추가 암호화(본인 비밀번호 기반)는 **구성원별 옵션**으로 둔다(5장).

남은 확인: 토스 약관상 공용 시세 수집의 허용 여부. [확인 필요]
