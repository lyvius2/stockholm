# 미러피시(MiroFish) 사전 실험 가이드

> 문서 지도: [docs/INDEX.md](INDEX.md) · 기준 문서: [PROJECT.md](../PROJECT.md) · 작업 규칙: [CLAUDE.md](../CLAUDE.md) · 개발 순서: [DEVELOPMENT_PLAN.md](DEVELOPMENT_PLAN.md)

작성: 2026-09-20 / 상태: 실험 전

## 목적

미러피시 연동(PROJECT.md F6, D13)을 설계하기 전에, 코드를 짜지 않고 미러피시를 Mac에서 직접 돌려 네 가지를 확인한다. 결과물이 매매 판단에 쓸 만한 품질인지, 1회 실행에 시간이 얼마나 걸리는지, 토큰 비용이 얼마인지, 그리고 외부 프로그램이 호출할 수 있는 API 형태가 어떤지다. 이 결과에 따라 미러피시를 토론의 주력 엔진으로 쓸지, 자체 페르소나 토론의 보조 엔진으로 쓸지를 정한다.

## 준비물

미러피시 원본 저장소는 github.com/666ghj/MiroFish 이고 라이선스는 AGPL-3.0이다. 소스 실행 기준으로 Node.js 18 이상, Python 3.11~3.12, Python 패키지 매니저 uv가 필요하다. Docker로 띄울 경우 Docker Desktop만 있으면 된다.

**관리형 설치(D13 개정) 검증을 겸한다.** 제품에서는 데몬이 `uv`로 Python을 받고 고정 커밋을 clone해 백엔드만 띄울 계획이므로, 실험도 같은 방식으로 한다: 시스템 Python·Docker 없이 `uv python install 3.12` → clone(커밋 해시 기록) → `uv sync` → 백엔드 단독 실행. 프론트엔드(Node)는 API 형태 파악용으로만 한 번 띄우고, 이후 실험은 **백엔드 API만으로** 전 과정을 재현한다.

외부 계정은 두 개가 필요하다. 하나는 OpenAI 호환 형식의 LLM API 키이고(원본은 알리바바 Qwen-plus로 테스트되었으나 호환 엔드포인트면 교체 가능), 다른 하나는 에이전트 메모리용 Zep Cloud API 키다. Zep Cloud를 쓰면 시드 자료와 시뮬레이션 기억이 외부 서비스에 저장된다는 점을 인지하고 진행한다. 이것이 꺼려지면 Neo4j + Ollama로 로컬화한 포크(nikmcfly/MiroFish-Offline)가 있으나, 메모리 사용량이 크고 원본과 동작이 다를 수 있으므로 1차 실험은 원본으로 한다.

## 설치와 실행

저장소를 클론한 뒤 환경 파일을 만든다. (Stockholm 저장소 바깥의 별도 폴더에서 진행한다.)

```bash
git clone https://github.com/666ghj/MiroFish.git
cd MiroFish
cp .env.example .env
```

`.env`에 `LLM_API_KEY`, `LLM_BASE_URL`, `LLM_MODEL_NAME`, `ZEP_API_KEY` 네 값을 채운다. 그다음 소스로 실행하려면 아래 두 줄이고,

```bash
npm run setup:all
npm run dev
```

Docker로 실행하려면 `docker compose up -d` 한 줄이다. 어느 쪽이든 프론트엔드는 http://localhost:3000, 백엔드 API는 http://localhost:5001 로 뜬다. 실험 시점의 커밋 해시를 반드시 기록해 둔다(이후 연동 시 버전 고정의 기준이 된다).

## 실험 시나리오

미러피시의 흐름은 다섯 단계다. 시드 자료로 지식 그래프 구축, 페르소나와 환경 설정, 시뮬레이션, 리포트 생성, 그리고 시뮬레이션된 에이전트와의 후속 대화. 사용자가 넣는 것은 시드 자료 파일과 자연어로 쓴 예측 요구사항 두 가지다.

**종목 선정.** 최근 한 달 안에 뚜렷한 이벤트(실적 발표, 대형 공시, 규제 이슈)가 있었던 국내 대형주 하나를 고른다. 핵심은 "이미 결과를 아는 과거 시점"으로 실험하는 것이다. 예를 들어 3주 전 시점까지의 자료만 넣고 이후 2주를 예측하게 하면, 실제 주가 흐름과 바로 대조할 수 있다.

**시드 자료.** 기준 시점 이전의 자료만 모아 하나의 문서(PDF 또는 텍스트)로 만든다. 해당 기업의 최근 분기 실적 요약, DART 주요 공시 2~3건, 기준 시점 직전 1~2주의 주요 뉴스 5~10건, 최근 3개월 주가와 거래량 요약, 업종과 거시 환경 요약 한 단락, 그리고 **"여론·수급" 절**(기준 시점 직전 1주의 StockTwits 심리 비율·메시지 수 또는 국내 수급 표, 대표 게시글 10~20건을 강세·약세 균형으로 발췌, "사실 검증되지 않은 여론"이라는 머리말) 정도면 충분하다. 기준 시점 이후의 정보가 섞이지 않도록 주의한다. 여론 절은 **한 번은 넣고 한 번은 빼고** 돌려, 리포트에 여론 인용이 나타나는지와 결론이 달라지는지를 본다([`docs/DEBATE_DESIGN.md`](DEBATE_DESIGN.md) 3.2).

**예측 요구사항 프롬프트.** 예시는 다음과 같다. "위 자료를 바탕으로, 서로 다른 투자 성향을 가진 시장 참여자들(가치투자자, 단기 모멘텀 트레이더, 기관 리스크 매니저, 매크로 애널리스트, 개인 투자자)이 이 종목에 대해 향후 2주간 어떻게 반응하고 논쟁할지 시뮬레이션하라. 최종적으로 매수/보유/매도 중 우세한 의견, 핵심 근거 3가지, 가장 강한 반대 논거, 판단을 뒤집을 수 있는 이벤트를 정리하라."

**실행 횟수.** 공식 문서가 소모가 크다며 40라운드 미만으로 먼저 돌려보기를 권하므로, 1차는 10~20라운드로 돌린다. 같은 입력으로 최소 2회 반복해서 결과가 얼마나 흔들리는지(재현성)를 본다. 여유가 되면 3차로 페르소나 구성이나 라운드 수를 바꿔 민감도를 본다.

## 기록할 항목

각 실행마다 다음을 남긴다.

| 항목 | 기록 방법 |
|---|---|
| 단계별 소요 시간 | 그래프 구축 / 환경 설정 / 시뮬레이션 / 리포트 각각 |
| 토큰 비용 | LLM 제공사 콘솔의 사용량을 실행 전후로 비교 |
| 메모리·CPU | 활동 모니터에서 Python, Node, Docker 프로세스 피크치 |
| 결과 품질 | 결론의 명확성, 근거의 구체성, 실제 주가와의 부합 여부 |
| 재현성 | 같은 입력 2회의 결론이 일치하는지 |
| 페르소나 품질 | 자동 생성된 에이전트들이 의도한 투자 성향을 반영하는지 |
| 여론 활용 | 시드 문서의 "여론·수급" 절을 에이전트가 인용하는지, 여론을 사실로 오인하는지, 절을 뺐을 때와 결론이 달라지는지 |
| API 형태 | 아래 참조 |
| 관리형 설치 가능성 | (a) 프론트엔드 없이 백엔드 API만으로 그래프 구축→시뮬레이션→리포트→후속 대화가 되는가 (b) 포트(5001)와 데이터 저장 경로를 환경 변수·설정으로 바꿀 수 있는가 (c) `uv`만으로 시스템 Python 없이 설치·실행되는가, 설치 용량·소요 시간 (d) 프로세스를 내렸다 올려도 프로젝트 상태가 유지되는가 (e) Zep Cloud 무료 한도로 토론 몇 회가 가능한가 |

**실시간 노출 여부.** 시뮬레이션 진행 중 에이전트들의 발언이 API나 화면에 실시간으로 나오는지, 리포트만 나오는지 확인한다. 또 사용자가 진행 중에 개입(질문·의견)할 수 있는 경로(후속 대화 기능 포함)가 있는지, 완료된 프로젝트를 이어서 실행할 수 있는지도 본다. 토론 창의 메신저 UI와 사용자 개입 설계(`DEBATE_DESIGN.md` 5.3)가 이 결과에 달려 있다.

**API 형태 파악.** 브라우저 개발자 도구의 Network 탭을 연 채로 전 과정을 진행하고, 프론트엔드가 5001 포트로 보내는 요청을 HAR 파일로 저장한다. 확인할 것은 프로젝트 생성·파일 업로드·시뮬레이션 시작·상태 조회·리포트 조회 각각의 엔드포인트와 페이로드, 장시간 작업의 진행 상황을 폴링으로 받는지 스트리밍으로 받는지, 리포트가 구조화된 JSON인지 자연어 마크다운인지, 인증이 있는지다. 이 HAR 파일이 이후 어댑터(`SimulationPort`) 설계의 1차 자료가 된다. HAR 파일에는 키가 포함될 수 있으므로 저장소에 커밋하지 않는다.

## 판단 기준

실험 후 다음 질문에 답한다. 첫째, 리포트가 "매수/보유/매도 + 근거 + 확신도"로 변환할 수 있을 만큼 결론이 명확한가. 둘째, 2회 반복의 결론이 같은 방향인가. 셋째, 1회 비용과 시간이 일상적으로(예: 관심 종목 5개를 주 2~3회) 돌릴 만한 수준인가. 넷째, API가 외부 호출에 무리 없는 형태인가.

관리형 설치 항목 (a)~(c)가 하나라도 부정이면 D13은 "외부 주소 등록"만으로 되돌리고 설치 자동화는 포기한다. 네 가지 품질 질문이 모두 긍정이면 미러피시를 토론의 주력 엔진으로 두고 자체 구현은 최소화한다. 품질은 좋은데 비용이나 시간이 과하면, 자체 페르소나 토론(가벼운 다중 LLM 호출)을 일상용으로 두고 미러피시는 중요한 이벤트 때만 돌리는 보조 엔진으로 둔다. 품질이나 재현성이 부족하면 미러피시 연동은 후순위로 내리고 자체 토론 엔진에 집중한다.

## 주의

이 실험은 시스템 설계를 위한 기술 검증이며, 한두 번의 과거 시점 대조로 예측력을 입증할 수는 없다. 실제 매매 연결 전에는 다수 종목과 기간에 걸친 기록·대조 단계를 별도로 거친다.
